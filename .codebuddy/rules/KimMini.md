# KVMini 项目开发规则

> 本文件为 KVMini 项目的持久规则，每次对话自动加载，所有开发活动必须遵守。

---

## 项目简介

KVMini 是一款基于 Tauri + Rust 的跨平台鼠标键盘共享软件，支持 Mac（M芯片/Intel）和 Windows。

---

## 开发前必做

1. **使用 superpowers**：采用 superpowers 开发，如果没有安装先安装
2. **阅读产品设计文档**：每次开发前阅读 `docs/plans/` 目录下的最新设计文档，再进行设计和开发
3. **遵循第一性原理**：明确对齐需求，确定问题本质，拒绝经验主义和路径盲从，不假设不完全清楚的目标，保持谨慎，有质疑和问题先与用户对齐，制定好开发方案再动手
4. **遵循奥卡姆剃刀原理**：代码要简洁高效，无过多冗余，每次开发都要审视是否有可以删除的多余代码
5. **确认兼容性**：开发前确保支持当前系统和版本（见兼容性规则）

---

## 开发规则

### 版本显示
- 所有程序界面必须能看到版本号
- 版本号来源：`package.json` 和 `src-tauri/Cargo.toml` 保持同步

### 代码质量
- 遵循奥卡姆剃刀：代码简洁高效，无冗余
- 每次开发前后都要审视整体代码，重构多余部分
- 函数单一职责，保持清晰可读

---

## 测试规则

1. **严格 TDD**：每次修改代码之前，先针对需求和修改写测试用例，再写实现
2. **持续维护测试**：开发完成后回归测试，能自测就自测，尽量不要让用户操作
3. **日志和调试**：开发阶段尽可能详尽增加日志和调试手段，有 bug 时先查询日志
4. **Bug 测试用例**：每个修复的 bug 都要增加一个新的测试用例
5. **Bug 文档记录**：记录 bug 内容、根因、修改方式、修改次数、出现次数（见 Bug 管理）
6. **修复前查清单**：修复 bug 前先阅读 `docs/bug-list.md`，看是否出现过这个 bug

### 反复出现的问题（3次以上）
- 先搜索资料寻找类似工程代码
- 找到根因，**停下来与用户对齐**
- 明确修改方法和修改范围
- 修复后加入记忆，重点关注

---

## Bug 管理

每个 bug 记录以下内容：

| 字段 | 说明 |
|------|------|
| 现象 | 用户看到的问题表现 |
| 根因 | 为什么会出现这个问题 |
| 修改方式 | 怎么改的 |
| 修改次数 | 该 bug 被修改了几次 |
| 出现次数 | 该 bug 出现了几次 |

Bug 清单文件：`docs/bug-list.md`（如不存在则创建）

## 版本规则

- 每次构建，版本号 +1
- 删除老的构建产物和安装包
- 构建产物名称加上版本号
- 版本更新命令：`npm run version:update`

```
版本格式：主版本.次版本.修订版本
每次构建：修订版本 +1
```

---

## 提交规则

1. **提交前 Code Review**：每次提交代码前，让另外一个 agent review 代码，包含重构和性能分析（使用 `requesting-code-review` skill）
2. **提交信息格式**：

```
[当前版本号] 需求清单总结

- 功能1: 描述
- 功能2: 描述
- 修复: 问题描述
```

---

## 兼容性规则

| 平台 | 要求 |
|------|------|
| Windows | 默认支持 |
| macOS M芯片 | 默认支持（aarch64-apple-darwin）|
| macOS Intel | 默认支持（x86_64-apple-darwin）|

- 开发前确认支持当前系统和系统版本
- 其他系统版本有兼容性问题，先与用户对齐
- 多版本适配时，不同版本的适配差异代码**务必做好隔离**，防止互相影响
- 有多版本适配要保证所有版本都能实现功能并通过测试

---

## 构建完成后

1. 自动构建（`npm run build`）
2. 生成完整的产品设计、开发总结和架构图
3. 按日期时间存档到 `docs/plans/` 目录
4. 启动程序验证

---

## 开发流程 Checklist

### 开发前
- [ ] 使用 superpowers（未安装先安装）
- [ ] 阅读 `docs/plans/` 最新产品设计文档
- [ ] 第一性原理对齐需求，有疑问先与用户确认
- [ ] 确认兼容性（Win / Mac M / Mac Intel）
- [ ] 写测试用例（TDD，先写测试再写实现）

### 开发中
- [ ] 实现代码，通过测试
- [ ] 增加日志和调试手段
- [ ] 遵循奥卡姆剃刀，删除冗余代码
- [ ] 界面显示版本号

### 提交前
- [ ] 回归测试全部通过（`npm test`）
- [ ] 版本号 +1（`npm run version:update`）
- [ ] 删除旧构建产物，构建新版本（`npm run build`）
- [ ] 让另一个 agent 做 Code Review（`requesting-code-review`）
- [ ] 提交信息格式：`[版本号] 需求清单总结`

### 提交后
- [ ] 生成产品设计、开发总结、架构图，存档到 `docs/plans/YYYY-MM-DD-xxx.md`
- [ ] 启动程序验证功能

## 常见错误

| 错误 | 后果 |
|------|------|
| 跳过 TDD，先写实现 | 隐藏 bug，测试覆盖不足 |
| 不读产品文档就开发 | 方向偏差，返工 |
| 不查 bug 清单就修复 | 重复修同一个 bug |
| 不做兼容性隔离 | 平台间代码互相影响 |
| 忘记更新版本号 | 版本混乱，无法追踪 |
| 不做 Code Review 就提交 | 代码质量下降，性能问题遗漏 |
