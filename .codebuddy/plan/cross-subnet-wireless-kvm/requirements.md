# 需求文档：跨网段无线键鼠共享

## 引言

### 背景与问题

KVMini 目前的设备发现机制依赖 **UDP 广播**（向 `255.255.255.255:8888` 发送 `KVM_DISCOVERY` 包），这种方式在同一网段内工作正常，但**广播包无法穿越路由器**，因此在以下公司内网场景中会失败：

```
笔记本（无线网段 192.168.1.x）  ←→  公司路由器  ←→  台式机（有线网段 10.0.1.x）
```

### 技术可行性

| 方式 | 跨网段可行性 | 说明 |
|------|------------|------|
| UDP 广播自动发现 | ❌ 不可行 | 广播包被路由器隔断 |
| 手动输入 IP + TCP 直连 | ✅ 可行 | 只要网络互通（能 ping 通），TCP 可跨网段 |
| 防火墙 | ⚠️ 需配置 | 对端需开放 KVMini 监听端口 |

**结论**：只要两台机器之间网络互通，通过手动输入对端 IP 地址发起 TCP 连接，完全可以实现跨网段键鼠共享。当前代码中 `connect_to_device` 仅支持连接已发现的设备，需要新增手动 IP 直连入口。

### 当前 Windows 支持状态

本次新增功能均为全新开发，**之前 Windows 版本不存在以下功能**：

| 功能 | 是否新增 | macOS | Windows | 备注 |
|------|---------|-------|---------|------|
| `connect_by_ip` 手动 IP 直连 | ✅ 新增 | ✅ | ✅ | 基于 tokio TCP，跨平台通用 |
| `get_network_interfaces` 获取网卡列表 | ✅ 新增 | ✅ | ⚠️ | Windows `ipconfig` 输出含 `(Preferred)` 后缀，需修复 |
| `set_listen_address` 监听地址配置 | ✅ 新增 | ✅ | ✅ | 基于文件 IO，跨平台通用 |
| `get_listen_config` 读取监听配置 | ✅ 新增 | ✅ | ✅ | 基于文件 IO，跨平台通用 |
| `get_local_ip` 获取本机 IP | 已有 | ✅ | ✅ | 已有 `ipconfig` 分支 |
| 前端 UI（手动连接 + 设置面板） | ✅ 新增 | ✅ | ✅ | HTML/JS/CSS 跨平台通用 |

**所有新增功能均需在 macOS 和 Windows 两端编写测试用例。**

## 需求

### 需求 1：手动输入 IP 地址直连（跨网段核心功能）

**用户故事：** 作为一名公司用户，我希望能够手动输入对端设备的 IP 地址发起连接，以便在自动发现失败（跨网段）时仍能建立键鼠共享。

#### 验收标准

1. WHEN 用户打开应用主界面 THEN 系统 SHALL 在设备发现面板中提供"手动连接"输入框，允许用户输入目标设备的 IP 地址（支持 IPv4）
2. WHEN 用户输入 IP 地址并点击"连接" THEN 系统 SHALL 绕过广播发现，直接向该 IP 的 KVMini 监听端口发起 TCP 连接，超时时间不超过 5 秒
3. IF 连接成功 THEN 系统 SHALL 显示连接成功提示，并将该设备加入已连接设备列表
4. IF 连接失败（超时/拒绝/不可达） THEN 系统 SHALL 显示具体错误原因（网络不通 / 端口未开放 / 对端未运行 KVMini），并给出操作建议
5. WHEN 用户输入 IP 地址 THEN 系统 SHALL 对输入内容进行 IPv4 格式校验，拒绝非法格式并给出提示
6. WHEN 用户通过手动 IP 成功连接 THEN 系统 SHALL 将该 IP、设备名称、连接时间保存到连接历史，下次可一键重连

---

### 需求 2：连接历史支持手动 IP 记录与快速重连

**用户故事：** 作为一名公司用户，我希望连接历史能记录手动输入的 IP 地址，以便每次上班时快速重连，无需重复输入。

#### 验收标准

1. WHEN 用户通过手动 IP 成功连接设备 THEN 系统 SHALL 将 IP 地址、设备名称、最后连接时间保存到本地历史记录
2. WHEN 用户打开应用 THEN 系统 SHALL 在连接历史列表中同时显示自动发现的设备和手动 IP 设备，并用图标区分
3. WHEN 用户点击历史记录中的某条手动 IP 记录 THEN 系统 SHALL 直接使用记录中的 IP 发起重连，无需重新输入
4. WHEN 历史记录中的设备无法连接 THEN 系统 SHALL 显示"不可达"状态，并允许用户手动编辑 IP 或删除该记录
5. IF 历史记录超过 20 条 THEN 系统 SHALL 自动清理最旧的记录，保留最近 20 条

---

### 需求 3：服务端监听地址配置（让对端能连进来）

**用户故事：** 作为一名公司用户，我希望能配置本机 KVMini 的监听地址，以便对端通过手动 IP 连接到我的设备。

> **说明：** 此功能为本次全新开发，之前 macOS 和 Windows 版本均不存在。需要在两个平台上同时实现并编写测试用例。

#### 验收标准

1. WHEN 用户打开设置面板 THEN 系统 SHALL 显示当前设备所有可用网卡及其 IP 地址列表，供用户选择监听接口
2. WHEN 用户选择"所有网卡（0.0.0.0）" THEN 系统 SHALL 在所有网卡上监听，允许来自任意网段的连接（推荐跨网段场景使用）
3. WHEN 用户选择特定网卡 THEN 系统 SHALL 仅在该网卡对应的 IP 上监听连接请求
4. WHEN 用户修改监听端口 THEN 系统 SHALL 验证端口范围（1024-65535），并在保存后重启监听服务
5. WHEN 服务端启动监听 THEN 系统 SHALL 在主界面状态面板中显示当前监听的 IP 地址和端口，方便用户告知对端
6. WHEN 为 `set_listen_address` 命令编写测试 THEN 系统 SHALL 在 macOS 和 Windows 两个平台的 `cargo test` 中均包含以下测试场景：
   - 合法端口（1024-65535）保存成功
   - 非法端口（< 1024 或 > 65535）返回错误
   - 配置持久化：保存后重新读取 `get_listen_config` 返回相同值
   - 选择"所有网卡（0.0.0.0）"时正确保存
7. WHEN 为设置面板 UI 编写测试 THEN 系统 SHALL 在 `npm test` 中包含以下测试场景：
   - 网卡下拉列表正确渲染（含"所有网卡"选项）
   - 端口输入框非法值时显示错误提示
   - 保存成功后主界面状态面板更新显示新的监听地址

---

### 需求 4：网络连通性检测与防火墙诊断

**用户故事：** 作为一名公司用户，我希望应用能在连接失败时给出具体的诊断信息，以便快速判断是网络不通还是防火墙拦截。

#### 验收标准

1. WHEN 用户发起手动 IP 连接失败 THEN 系统 SHALL 自动执行诊断，区分以下情况并给出对应提示：
   - 网络不可达（路由不通）→ 提示"请检查两台设备是否在同一公司内网"
   - 端口被拒绝（Connection Refused）→ 提示"对端 KVMini 未运行或端口未开放"
   - 连接超时 → 提示"可能被防火墙拦截，请检查 Windows Defender / macOS 防火墙设置"
2. WHEN 连接建立后 THEN 系统 SHALL 持续监测连接延迟（RTT），并在界面上实时显示
3. IF 连接延迟超过 50ms THEN 系统 SHALL 以黄色警告色显示延迟值，提示用户网络质量较差
4. IF 连接中断 THEN 系统 SHALL 自动尝试重连（最多 3 次，间隔 2 秒），重连失败后通知用户

---

### 需求 5：跨平台一致性（macOS 与 Windows）

**用户故事：** 作为一名用户，我希望跨网段连接功能在 macOS 和 Windows 上行为完全一致，以便在混合办公环境中无缝使用。

#### 验收标准

1. WHEN 手动 IP 连接功能在 macOS 上实现后 THEN 系统 SHALL 同步在 Windows 上实现相同功能，界面和交互保持一致
2. WHEN 防火墙规则需要配置 THEN 系统 SHALL 在 macOS 上提示用户允许应用通过防火墙，在 Windows 上提示允许 Windows Defender 防火墙例外
3. WHEN 运行跨平台功能检查脚本 THEN 系统 SHALL 验证手动连接、历史记录、网络诊断、监听配置四项功能在两个平台上均已实现
4. IF 某平台的网络 API 存在差异 THEN 系统 SHALL 通过平台抽象层封装，前端调用方式保持统一
5. WHEN 在 Windows 上调用 `get_network_interfaces` THEN 系统 SHALL 正确解析 `ipconfig` 输出，包括处理 IP 地址后的 `(Preferred)` 后缀（如 `192.168.1.100(Preferred)`），确保返回干净的 IP 字符串
6. WHEN 在 Windows 上调用 `get_local_ip` THEN 系统 SHALL 同样处理 `(Preferred)` 后缀，确保显示正确的 IP 地址
7. WHEN 为所有新增 Rust 命令编写单元测试 THEN 系统 SHALL 确保测试在 macOS 和 Windows 两个平台的 CI 环境中均能通过，不得使用仅在单一平台可用的 API 或路径格式
8. WHEN 为设置面板功能编写测试 THEN 系统 SHALL 在 `npm test` 中覆盖 macOS 和 Windows 两端的行为差异（如网卡名称格式差异），确保前端逻辑对两端返回数据均能正确处理
